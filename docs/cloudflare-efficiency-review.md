## キャッシュは「どこで効くか」を分ける

- **静的 HTML/JS/CSS:** Static Assets のブラウザーキャッシュとハッシュ付きファイル名を維持する。Worker を静的要求に通す、あるいはサービスワーカーを足す理由はない。[Static Assets 既定ヘッダー](https://developers.cloudflare.com/workers/static-assets/headers/)・[現行設定](../public/_headers#L1-L13)
- **景品画像:** R2 カスタムドメインから配信する JPEG/PNG/WebP は、Cloudflare CDN の既定キャッシュ対象拡張子に含まれる。オブジェクトには `public, max-age=31536000, immutable` を付けている。本番の確認対象画像は GET で HIT したので、その画像について新しい Cache Rule は不要。他の画像や POP で継続的な MISS が測定された場合だけ、ホストと `/prizes/` に絞った **zone Cache Rule** や Free の Smart Tiered Cache を検討する。Cache Rules は Free で 10 件まで。[既定キャッシュ](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/#default-cached-file-extensions)・[R2 カスタムドメイン](https://developers.cloudflare.com/r2/buckets/public-buckets/#caching)・[Cache Rules](https://developers.cloudflare.com/cache/how-to/cache-rules/#availability)・[Tiered Cache](https://developers.cloudflare.com/cache/how-to/tiered-cache/#availability)
- **状態 API:** `Cache-Control: no-cache` と ETag/304 はクライアントとの転送量を減らすが、再検証の Worker/DO 要求と ETag 用のシリアライズ・SHA-256 は消さない。PITR 後に revision が以前と一致しても内容が異なる場合があるため、revision だけで共有キャッシュ化しない。公開 WebSocket の初期 state と切断時の bounded HTTP fallback を維持する。Admin/Screen は Access の認証境界も維持する。[ETag](../worker/http.ts#L173-L200)・[PITR の回帰テスト](../test/worker.integration.test.ts#L122-L144)・[クライアント復旧](../src/lib/realtime.ts#L278-L320)
- **新しい Workers Cache:** Worker 単位のキャッシュで zone Cache Rules とは別。ヒット時は Worker の CPU を節約できる一方、**有効化すると静的アセットのヒットも Workers リクエストに計上**される。現在の Worker は動的状態と認証付き画面が中心。ヒット時に Worker 側の Access 検証を通らない設計を作るリスクもある。今は有効化せず、`caches.default` を自前で組み込むこともしない。[Workers Cache の対象・課金](https://developers.cloudflare.com/workers/cache/#pricing)・[設定](https://developers.cloudflare.com/workers/cache/configuration/)

## YAGNI レビュー：採用順に絞る

1. **既存の再利用:** スモークでは受信 ETag をそのまま `If-None-Match` に渡して 304 を確認する既存の手順を維持し、別の ETag 計算は増やさなかった。`ReactionHub.getStatus()` はリポジトリ内の利用箇所が見当たらないが、配備先に外部 RPC 利用がないことは確認できていないため、削除を見送った。[スモーク](../scripts/cloudflare-smoke.mjs#L107-L118)・[保留したメソッド](../worker/reaction-hub.ts#L99-L111)
   - 条件付きの重複: `/api/bingo/prizes` は現在の UI で使われず、スモークが読む `/api/bingo/state` に景品も含まれる。外部 API 利用者がいないことを確認できた場合だけ、スモークで取得済みの state を再利用して専用ルートを削る。未確認のまま公開契約を消さない。[ルート](../worker/index.ts#L71-L76)・[投影](../worker/index.ts#L157-L193)・[スモーク](../scripts/cloudflare-smoke.mjs#L97-L121)
2. **標準ライブラリ:** `sha256Hex` は画像用 `Uint8Array<ArrayBuffer>` を複製せず標準の `crypto.subtle.digest` に渡す。アップロード画像は最大 5 MiB で、従来の `Uint8Array.from(value)` による同サイズの一時コピーを除いた。ハッシュ・MIME・magic bytes・サイズ検査は維持。Worker の `crypto.randomUUID()` も、正常要求では生成せず例外処理時だけ生成する。性能差は未計測で、大きな高速化とは扱わない。[ハッシュ](../worker/http.ts#L166-L169)・[画像入力](../worker/images.ts#L21-L40)・[ID とログ](../worker/index.ts#L86-L115)
3. **Cloudflare ネイティブ機能:** SQLite DO、`acceptWebSocket` による休止、`setWebSocketAutoResponse`、Static Assets、R2 カスタムドメイン、`/cdn-cgi/image/` はすでに利用済み。KV/D1/Queues、毎日 Cron、独自 CDN/画像プロキシを追加すると、固定名の状態正本と新たな整合・無料枠管理が増える。現時点では不要。カスタム Cache Rule も画像の本番 MISS を確認した場合に限る。[構成](../wrangler.jsonc#L13-L40)・[休止対応](../worker/game-state.ts#L615-L638)・[運用上の非採用](cloudflare-operations.md#L15-L23)
4. **既存依存:** Access JWT の検証には導入済みの `jose` を使い、鍵の取得・キャッシュ・署名検証を自作しない。画像表示は既存の `<img>`、`srcSet`、`loading`、`alt` で足りるため、新たな画像コンポーネント依存は不要。アクセシビリティ属性は保持。[Access](../worker/access.ts#L1-L65)・[画像](../src/components/ui/ResponsiveImage.tsx#L22-L55)
5. **最小コード:** stamp の RPC 応答から未使用の `dailyCount` と SQL の `RETURNING daily_count` を削除。永続化された日次カウンターと公開 API の応答は維持した。17 個の `srcSet` 幅や景品ページの `preload` を「必ず17回課金」「二重 fetch」と決めつけない。保存済み Lighthouse では state GET は 1 件。画像変換件数や端末幅の実測後に候補幅を絞るか判断する。[stamp 結果](../worker/domain.ts#L26-L32)・[呼び出し側](../worker/index.ts#L246-L253)・[画像幅](../src/components/ui/ResponsiveImage.tsx#L5-L35)・[preload](../src/features/user/prizes/prizes-page.tsx#L8-L12)

**削ってはいけないもの:** Admin/Screen の Access policy と Worker 側 JWT/AUD 検証、Turnstile のサーバー側検証、リーチ重複排除、画像の容量・形式・ハッシュ検査、WebSocket 切断後の HTTP fallback、Screen socket の認証期限、PITR、`ReactionHub` の分離、画像の `alt`/遅延読み込み。いずれも無料枠最適化のための代用品ではない。[運用上の不変条件](cloudflare-operations.md#L15-L23)・[Access](../worker/access.ts#L14-L110)・[画像](../worker/images.ts#L17-L60)

## 次の確認と限界

スモークの ETag 期待値は修正した。隔離ランタイムで state 200→304、画像アップロード 201→画像 GET 200→304、stamp 201 を確認し、`pnpm fmt:check`、`pnpm lint`、`pnpm typecheck`、`pnpm test`（63件）、`pnpm knip`、`mise run cloudflare:check` が通った。本番へのデプロイと `mise run smoke` は行っていない。イベント前に Workers/DO の account 合算 request・CPU 上限違反・SQLite read/write、R2 Class B、Images の一意変換件数、Access seat を再確認する。数値が無料枠に近づかない限り、新規サービスを追加せず、既存の WAF 停止スイッチと紙運用を優先する。[当日手順](cloudflare-operations.md#L141-L175)・[復旧](cloudflare-operations.md#L218-L253)

本調査は本番 GraphQL 推定値と公開画像の GET を読み取ったが、実アカウントの契約プラン、ゾーン Cache Rule、Images の請求上の一意件数、DO の課金対象 SQLite 行数、開催日の実トラフィックは確認できていない。1000 socket の容量試験も実施していない。「イベント当日も全枠内」「全画像で HIT」「画像アップロードの CPU が 10 ms 未満」という断定はしない。ローカルの機能確認、平時の本番スナップショット、無料プランの上限を混同しないこと。
